# WIRE-R19：GitHub CI 走線搜尋超限

## 失敗證據

R18 的 GitHub [run 9](https://github.com/s950329/wiring-panel-simulator/actions/runs/34929728564) 在 Node 22.16.0 的 `npm test` 中，213 項測試有 212 項通過、1 項失敗。失敗項目是 R8 23 線案例的刪線、反向重接及閉合專案匯出／匯入；最後一條 `TB1:27B → PB2:1` 達到走線搜尋上限。測試合計約 424.7 秒，後續 build／browser 步驟未執行。R17 的 [run 8](https://github.com/s950329/wiring-panel-simulator/actions/runs/34925520455) 也有同類規劃時間超限。

先前 R18 的 213 項全部通過是本地 Node 24.19.0 的結果（約 192 秒），並非 GitHub CI 通過。沒有等遠端驗證結束即完成交付，留下了這個驗證缺口。CI 的安裝成功、引用的 fixtures 皆已追蹤；不是缺少附件或建置檔案。執行速度差異已確認，但不將差異全部歸因於 Node 版本。

## 根因與最終修正

1. 局部網格同時受 10,000 步與 450 ms 限制。時間可能在不同搜尋位置截斷路徑及替代候選，使結果受機器速度影響。移除局部 450 ms 判斷，改以原本的固定步數限制工作；時間僅記錄於診斷。
2. 完整線組遇到局部預算不足後，先試多個相近的局部重排／變體，較不同的全組排序排在第 6 個候選。重現案例在這個排序完成前已耗盡每姿態 20 秒。第一次 `ROUTE_SEARCH_LIMIT` 後，現在先給穩定的全組排序一次機會，再回到其他局部候選。`ROUTE_NOT_FOUND` 仍保留局部修復優先。

保留 10,000 搜尋步數、每 64 步 checkpoint、32 組候選、每姿態 20 秒總上限、碰撞／線距／板背／端子檢查和原子還原。這是有限範圍的路徑搜尋；未找到路徑不表示已證明物理上無解。沒有增加失敗快取，也沒有改低 CI 併行數或放寬測試斷言。

CI 仍使用原有 Node 22.16.0。依使用者既有指定，瀏覽器／WebGL 驗收由使用者執行，CI 的必跑項目對齊程式、實際幾何、正式與離線建置；瀏覽器腳本保留供手動使用。原始碼 artifact 改名為 `wiring-panel-source.zip`，以同包的 `verified-commit.txt` 識別來源，避免繼續錯標 R14。

## 重現與回歸

- 使用實際 23 線刪除／反向重接後的端點順序，Node 22.16.0、`Date.now` 相對實際時間加速 2 倍；這是讓相同計算較早接近上限的可控重現，並非聲稱完整模擬 CI 的硬體或排程。
- 舊排序在約 20.4 秒實際時間失敗於同一條第 23 線；只移除 450 ms 仍失敗。最終修正在約 18.5 秒完成整份匯入，保留原 20 秒的每姿態上限。
- `qa/panel-grid-check.mjs` 新增控制時鐘的測試，同一障礙物與 variant 0／3 必須保持相同路徑、搜尋步數及碰撞工作量；舊局部截止會回傳 null，修正後通過。原有步數上限、耗盡和取消測試保留。
- `qa/panel-planner-check.mjs` 於原本的實際匯入測試觀察規劃診斷，要求耗盡局部預算後及時嘗試不同的全組排序。只觀察真正的規劃呼叫，不替換求解器、碰撞、deadline 或路徑。新增斷言在舊排序失敗。

同步搜尋仍只在接線之間讓出事件迴圈，這次沒有宣稱瀏覽器取消變成即時，也未新增柔性線材物理或 WebGL 視覺驗收。

## 本地驗證結果（2026-09-15）

以 CI 相同的 Node 22.16.0 重新執行 `npm ci`、`npm test`、`npm run build`：安裝成功，214 項測試全部通過、0 失敗、0 跳過（約 212.2 秒）；正式建置及 R19 離線 HTML 的語法／逐位元組一致性驗證成功。新增的兩項回歸斷言已分別確認舊行為失敗。遠端 CI 的結果應以對應提交的 GitHub Actions 紀錄為準，不能以此本地紀錄代替。
